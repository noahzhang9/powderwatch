# PowderWatch

Personal ski-forecast and snowpack dashboard for Crystal Mountain, Snoqualmie / Alpental, Stevens Pass,
Whistler Blackcomb and Verbier.
It compares deterministic models, regional high-res models and ensembles from
[Open-Meteo](https://open-meteo.com/), runs them all through one set of snow physics, and tracks
station snow depth against each station's own history, with an ensemble-driven snowpack projection.

Design, data sources, methods and roadmap: [docs/proposal.md](docs/proposal.md). Conventions and invariants for contributors and coding agents: [AGENTS.md](AGENTS.md).

## Run locally

```bash
npm install
npm run obs        # fetch station observations → public/data/obs/*.json (≈30 s; BC archives cached in .cache/)
npm run dev        # http://127.0.0.1:5173 (hot reload)
# or
npm run build && npm run snapshot && npm run preview   # http://127.0.0.1:4173
```

Both servers bind to 127.0.0.1 only. `npm run snapshot` is optional locally: without it (and in
`npm run dev`) the browser calls Open-Meteo directly. Run it after `npm run build`, which empties
`dist/`. It also keeps a copy in `.cache/fc/`, so later local previews need no new Open-Meteo calls:

```bash
npm run preview:local   # snapshot-only build from .cache/fc/, served on http://127.0.0.1:4173
```

The snapshot-only build (`VITE_SNAPSHOT_ONLY=1`) uses the local snapshot at any age and never calls
Open-Meteo. Anything the snapshot doesn't hold says "Not in the local snapshot (snapshot-only mode)",
and a banner shows how old the snapshot is. The deploy workflow never sets the flag.

## Checks

```bash
npm test                               # unit tests (physics, stats, climatology, snowpack, time zones, snapshot URL parity, cache fallback,
                                       # verification record and its validator)
npm run typecheck
npx tsx scripts/backtest-snowpack.ts   # snowpack calibration/backtest against SNOTEL (≈2 min)
```

## Data refresh and deployment (GitHub Pages)

`.github/workflows/refresh-and-deploy.yml` runs every 4 hours at 20 minutes past (00:20, 04:20, …
20:20 UTC), on every push to `main`, and with a full station-history refresh in the Sunday 00:20 run: refresh
observations → commit `public/data` only if a reading changed → test → build → forecast snapshot →
deploy `dist/` to GitHub Pages. Actions are pinned to commit SHAs and each job gets only the
permissions it needs.

- **Station observations** are static JSON regenerated by `npm run obs` and committed.
- **Forecast snapshot** (`npm run snapshot`, `scripts/snapshot-forecasts.ts`) runs in the read-only
  build job after `npm run build`. It fetches the Open-Meteo responses the first screens need and
  writes them to `dist/data/fc/` with a `manifest.json` that maps each request URL to its file and
  fetch time. The snapshot ships only with the Pages deploy; it is not committed.
  - Covered: per resort, the deterministic forecast for all three bands, the pressure profile and
    all six ensembles at mid-mountain, run timing for every model, the previous run of each global
    model for the run-change panel, the last-7-days requests, and the snowpack-projection inputs
    at the station each Snowpack tab opens by default, then at the other stations while the budget
    allows. Run-history past runs and base/summit ensembles are always fetched live.
  - The browser builds every request URL with the same functions as the script
    (`src/lib/openmeteo.ts`, `src/lib/requests.ts`). `cachedJson` (`src/lib/cache.ts`) reads the
    manifest once per page and uses a snapshot copy younger than 4.5 hours instead of calling
    Open-Meteo. For anything missing or older it calls Open-Meteo as before and, if that fails
    (e.g. HTTP 429 on a shared network), falls back to the older snapshot copy.
  - The script sends a User-Agent with `PW_CONTACT`, makes at most 3 concurrent requests paced
    under the free tier's per-minute limit, retries 429/5xx with backoff, and logs requests, bytes
    and Open-Meteo's weighted call cost (`X-RateLimit-Cost`). Each run has a budget of 1,250
    weighted calls (`SNAPSHOT_MAX_COST`), raised when needed to fit the first screens, so the six
    scheduled runs use about 7,500–7,800 of the free tier's 10,000 a day and leave room for a push
    or manual run. Lower-priority groups are skipped when the budget runs out. A failed or partial
    snapshot never blocks the deploy; the browser fetches whatever is missing.

## Forecast-verification archive

Each snapshot run also builds a verification record from the responses it fetched (no extra
Open-Meteo calls): for the newest 00Z/12Z cycle that every current global model has run, the
forecasts for local days 1–10 at each resort's mid band (blend and each model) and at each station's
own point (each snowpack-scenario model), with ensemble quantiles and the "Chance of snow totals"
chances. `scripts/verification.ts` builds it; docs/proposal.md §6 lists every field.

- The read-only build job writes it to `.cache/verification/<cycle>.json` (never into `dist/`) and
  uploads it as an artifact.
- The `archive` job (`contents: write`, no npm code) validates it with
  `scripts/validate_verification.py`, re-serialises it and commits it to the **`data/verification`**
  branch as `cycles/YYYY-MM/<cycle>.json`. It creates the branch as an orphan on first use and never
  overwrites a file, so each cycle keeps the record from the first run that carried it. `main` never
  holds archive data, and the deploy doesn't wait for the archive.
- Read it with `git fetch origin data/verification` and
  `git worktree add ../powderwatch-verification data/verification`.

**One-time backfill.** `npm run backfill:verification` reads Open-Meteo's Previous Runs API at each
station that reported since the start of the window (each scenario model's forecast for every past
day, 1–7 days ahead) and writes `.cache/verification-backfill/<date>.json`. It refuses to run when
its estimate exceeds 1,500 weighted calls; 2026-10-01 to 2026-11-19 at 14 stations costs 535.5. It
pushes nothing. Once the first `archive` run has created the branch, add the files to it:

```bash
git fetch origin data/verification
git worktree add ../powderwatch-verification data/verification
python3 -I scripts/validate_verification.py --kind backfill .cache/verification-backfill ../powderwatch-verification
cd ../powderwatch-verification
git add backfill && git commit -m "chore(data): Backfill verification archive from Previous Runs" && git push origin data/verification
```

One-time setup:

1. Create a **public** GitHub repository (Pages on a free account requires public) and push `main`.
2. Repo **Settings → Pages → Build and deployment → Source: GitHub Actions**.
3. Run the workflow once from the **Actions** tab (or push). The site appears at
   `https://<user>.github.io/<repo>/`.

The site and repository are public. Trips are stored only in each visitor's browser.
GitHub disables scheduled workflows in public repos after 60 days without commits; the data
commits keep it active, and the workflow can be re-enabled from the Actions tab if it ever lapses.

## Layout

```
src/config/     models, resorts (bands, model lists, links), stations
src/lib/        physics, forecast blend, ensembles, snowpack model, climatology, Open-Meteo client, cache
src/views/      Dashboard, StormView, HistoryView, SnowpackView, About (methods)
src/lib/requests.ts  which Open-Meteo requests each view makes (shared with the snapshot script)
scripts/        fetch-obs.ts (station ingest), snapshot-forecasts.ts + snapshot-plan.ts (forecast snapshot),
                verification.ts + validate_verification.py + backfill-verification.ts (verification archive),
                backtest-snowpack.ts (calibration)
public/data/obs station daily series (generated)
dist/data/fc    forecast snapshot (generated at deploy, not committed)
```
